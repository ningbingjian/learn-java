## 后端HTTP覆盖

`RequestBoundaryHttpTests`在真实随机端口上使用Java HttpClient。常规请求不跟随重定向、不保存Cookie；测试凭据只覆盖测试上下文，不替换普通启动的随机密码。

保留第三课19项场景，并把有效身份访问未知路径的预期从404改为403：公开GET及安全头、参数400/修复200、近似路径、匿名及正确/错误Basic、未知用户、畸形Basic、独立匿名、JSON/HTML/后备Accept、实际生成登录页等均回归。

新增6项测试：

1. 有效身份访问近似路径、尾斜线、未知路径、错误代理前缀和外部`/error`均为403，未返回公开或问候业务内容，没有Basic认证挑战。
2. 同一路径OPTIONS匿名401、有身份403，不继承GET公开规则。
3. HEAD匿名401且无响应体、有身份403，不把MVC对HEAD的支持当成安全许可。
4. 无CSRF令牌POST得到403；外部匿名直接GET `/error`仍401，证明ERROR分派许可不等于公开错误路径。POST拒绝不用于证明路径授权。
5. 默认登录CSS可读，近似登录/样式路径仍拒绝。
6. 真实读取生成登录页CSRF字段，在同一Cookie上下文提交POST `/login`后，再凭Cookie访问已列入的GET `/hello`得到200。只作为框架入口兼容性回归。

本课的已认证403沿用框架默认拒绝处理，没有扩展第三课的业务错误代码清单，也不要求Boot默认错误体字段固定。CSRF保持开启。

## 编写时发现的边界与修复

首次浏览器OPTIONS得到204，而后端直连测试得到401。核对安装的Vite8.2.2源码，发现默认CORS中间件在代理前直接响应OPTIONS；本课同源观察台设置`server.cors: false`后，请求进入后端，浏览器得到真实401 JSON。修复后完整9项浏览器回归及独立跟写均通过，正文说明了这个差异，未把开发代理204解释为安全授权放行。

固定标签源码核对了Security7.0.7的路径匹配构造、有序映射首次命中返回、登录入口许可和默认样式过滤器。相关入口与解释放在正文对应位置；没有宣称所有编码路径、Servlet映射或框架版本都相同。
