# 01 课程文档写作规范

[返回学习路线总导航](00-学习路线总导航.md)

本规范约束 `learn-java-course` 下各阶段、技术模块与单课文档的新增、续写和重构，供人工作者与参与编写的 AI 共同遵守。模块可以补充自身要求；通用规范在本文件集中维护。

课程面向按路线学习的中文读者。最终质量标准是：**学生能够依据讲解独立完成操作，并解释为什么这样做、结果为什么如此、条件变化后如何判断。** 标题齐全、代码可运行、篇幅足够长，都不能单独证明教学完成。

## 1. 课程层级与学习目标

沿用总导航中的层级含义，不另造一套相互冲突的编号体系。

| 层级 | 必须说明的内容 | 深度安排 |
| --- | --- | --- |
| 阶段／专题 | 学习方向、阶段目标、所含模块及其关系 | 给出领域范围与成长方向 |
| 技术模块 | 技术边界、学习基础、递进顺序、完成后的能力 | 软件技术从基础使用逐步深入到原理、核心源码、扩展、诊断、优化与工程应用 |
| 单课 | 承接什么知识、解决什么明确问题、学完能够做什么 | 聚焦本课核心机制，控制同时引入的新概念 |
| 课内小节 | 当前问题、必要理论、实现与验证过程、结论 | 按理论、带原理的实操、小总结展开 |

模块需要同时具备广度和深入路径，不用一节概览代替整项技术的学习。深入顺序按依赖安排，不要求读完某技术全部源码才能进入下一技术。

学科、协议和架构方法按概念、推导、实现与验证组织；需要读源码时选择明确的具体实现。源码不可获取的技术，应说明可验证范围，不能编造内部实现。

每课目标应能观察或检查，例如“能区分定义登记与实例创建，并定位一次属性填充失败”，避免只写“了解 Spring”“掌握核心原理”等笼统目标。

## 2. 单课的基本组织方式

一课依次组织以下内容，标题名称和小节数量可根据内容调整。

1. **本课导入**：承接前课，解释当前问题、学习目标与必要的准备。
2. **分节教学**：每个承载核心学习内容的小节，按“理论 → 实操中解释原理 → 小总结”推进。
3. **整课总结**：把各节知识连成整体，归纳结论、边界和应用方法。
4. **理解检查与后续衔接**：检查学习效果，说明下一课继续解决什么问题。

理论与实操以小节为单位交替推进。不要将整课所有理论集中堆在开头，也不要先给出完整项目，再在末尾统一解释。

环境准备、导航等辅助段落无需机械套用三段结构。没有必要写代码的概念或架构小节，可以使用关系分析、执行推演、配置对照、故障材料或方案比较来完成应用与验证，不为满足形式编造代码。

## 3. 根据知识地位安排讲解深度

| 内容类型 | 讲解要求 |
| --- | --- |
| 前课已经讲过的知识 | 简要复述本次需要的原理，必要时链接具体前课，不重复整篇讲解 |
| 首次出现的辅助知识 | 解释到足以读懂当前代码、操作和结果，说明它在当前过程中的作用 |
| 本课核心知识 | 详细讲清概念、需求来源、处理机制、因果关系、适用条件与边界 |
| 后续才深入的知识 | 交代当前必须知道的作用及后续位置，不提前堆满实现细节 |

核心理论不能只给定义、用途和 API 名称。要能帮助学生推演接下来的实现：关键数据保存在哪里，由谁处理，处理发生在什么时点，为什么采用当前方式，条件变化会影响什么。

这些问题用于判断解释是否充分，不要求每个知识点都复制同一组问答标题。理论应围绕当前问题形成连贯说明。

本课必需的解释应当出现在正文。参考页用于补充额外变体与深入边界，不能让学生必须跳到参考页才看得懂当前步骤。

## 4. 实操必须带着原理逐步展开

### 4.1 修改前说明目的与依据

每次关键修改前，说明当前缺少什么能力，准备修改哪里，以及这次修改如何利用刚讲过的机制。一次修改尽量围绕一个清楚的学习目标，避免同时改变多个互不相关的条件。

当前示例能回答的问题应与本课目标一致。业务背景帮助理解技术，不应引入大量与当前知识无关的需求、框架或基础设施。

### 4.2 代码出现时解释关键过程

在核心代码对应的位置解释参数来源、对象关系、状态变化、调用顺序和处理责任。不要只把语法翻译成中文，也不要将关键解释全部推迟到运行结果之后。

已有知识可以简短提醒；首次出现、影响理解的关键语法或 API 应说明作用。例如工厂方法参数由谁提供、字段赋值保存的是哪一个引用，不能因为代码行数少就省略。

完整文件可以用于跟写和核对，但必须指出本步新增或改变的部分。较长文件应先讲当前改动，再按需要提供完整版本。避免学生只能整段覆盖文件，却不知道这一步改变了什么。

### 4.3 运行前推演，运行后解释

运行前提供足够的理论依据，让学生能够预测关键结果；预测不应变成尚未讲解机制的猜谜。

运行后把观察结果对应到处理过程，说明是哪项配置、哪段代码或哪次状态变化导致结果。区分“输出相同”“引用相同”“定义相同”等不同证据，不从一个现象直接推出过大的结论。

若输出顺序不构成技术契约，应说明当前示例的限定条件。只摘录部分日志时，注明是稳定摘要；不要把编写者预想的输出冒充实际运行结果。

### 4.4 错误实验要完整闭合

失败实验按教学需要设置。引入时先说明正在验证哪个机制；失败后定位发生阶段、异常含义和根因，再在原位置修复并交代正常状态。

故意错误不能成为后续默认代码。若保留独立失败样例，要与正常入口隔离，明确运行方式和预期失败。

## 5. 小总结与整课总结都必须有

### 5.1 小总结收拢当前知识

每个核心教学小节结束时，用简洁文字收拢刚刚建立的机制和结论，必要时点出最容易误用的条件。小总结不重复整段代码，也不只写“本节学习了某注解”。

### 5.2 整课总结建立整体理解

整课最后必须有明确的“本课总结”，至少涵盖以下内容：

- 本课解决了什么问题，形成了什么能力。
- 核心概念怎样联系，形成怎样的执行过程、推理过程或设计关系。
- 必须记住的结论及其适用边界。
- 如何用于实际开发、配置、诊断或设计判断。

总结应帮助学生脱离逐步跟写的细节，重新看清完整机制。适合比较的结论可以整理成表格；具有真实分支或调用关系的内容可以使用简洁图示。

整课总结不能只是拼接各节小总结，不能只列术语或回顾改过哪些文件，也不能用几道自查题代替解释。总结中不首次引入必须详细理解的新核心机制。

理解检查可以放在总结之后，或结合总结提出。涉及预测、修改、诊断的题目，应让学生使用已讲过的原理，而不是依赖尚未介绍的知识。

## 6. 原理与源码系列的写作要求

软件模块必须安排从基础到深入实现的递进路径，但并非每一节入门课都要求展开源码。是否进入源码取决于本课目标和读者准备程度。

进入源码时采用“机制问题 → 版本与入口 → 关键数据及分支 → 运行验证 → 结论”的顺序：

1. 先提出当前示例中需要解释的问题，说明读这段源码要确认什么。
2. 锁定与运行依赖匹配的版本，给出准确的类、方法或实现位置；源码链接尽量固定到标签或提交。
3. 解释关键参数、变量和数据结构各表示什么，区分配置描述、运行状态与实际业务对象。
4. 说明实际进入哪个分支、条件为何成立、执行后状态怎样变化。调用链应按职责分段，不只罗列方法名。
5. 给出可执行的观察办法，例如业务断点、框架断点、配置对照或可重复实验，再把证据连接回最初问题。

不要仅堆贴源码、截图和调用栈。也不要将某一次调用经过的分支描述成所有情形都必经的流程。调试表达式可能触发创建或改变状态时，必须交代这种影响。

“实现了一个简化模型”和“真实框架内部这样实现”要明确区分。简化模型应说明省略了哪些当前不研究的职责，不得凭模型推断真实实现的全部行为。

## 7. 面向中文初学者的表达

首次出现术语时先用中文说明含义，再给出英文名称、缩写或源码标识。关键术语在模块内保持一致，避免同一概念频繁更换译名。

使用完整、连贯的解释，避免连续引入多个新术语后默认学生已经理解。已有 Java 基础、Maven 等知识按路线复述必要部分，不把每课重新写成所有前置技术的入门课。

结论要带条件，避免“加了注解就会生效”“容器只有一个对象”“配置正确就一定启动成功”等省略处理阶段和适用范围的表述。

类比只用于帮助进入概念，随后要回到真实机制。图表用于说明关系、时序或比较，不以插图数量作为教学质量标准。

## 8. 示例连续性与工程组织

模块内尽量使用连续演进的示例。沿用前课内容时，指出哪些文件和能力继续使用，本课增加什么、暂时不研究什么。需要独立实验时说明原因、入口以及实验完成后回到哪个版本。

跟写步骤必须交代路径基准、命令执行目录、运行入口、文件是新增还是替换，以及其他文件应保持哪个状态。引用前课学生自行创建的文件时，要明确它们不是当前仓库中已经存在的文件。

完成版源码可以供对照，首次学习路径仍应支持逐步实现。跟写文件与完成版同时存在时，说明包、资源、扫描或运行入口的边界，避免互相污染。

沿用模块已有工程组织。若已有 Maven 聚合与多模块工程，新增课程应接入相应结构；不因写一节课就重复创建无关构建体系。其他技术按其模块的实际工具链组织，不照搬 Spring 示例的版本和目录。

保持现有阶段、模块和单课编号。新增普通课程文档按“序号 + 标题”命名；`README.md`、`AGENTS.md`、构建文件等约定文件名保持原用途。结构调整时同步修复导航与相对链接。

## 9. 技术准确性与验证

### 9.1 技术依据

涉及框架版本、默认行为、源码流程或容易混淆的边界时，核对与课程版本对应的官方文档、源码或实际运行。引用应靠近相关解释，便于读者追溯；推断与已验证事实要区分。

课程中说明使用的版本和必要环境。版本升级后应检查受到影响的示例与解释，不把旧输出直接标为新版本验证结果。

### 9.2 示例验证

新增或修改可执行示例时，验证与本次改动相关的跟写路径，包括有依赖的中间步骤。故意失败应确认在预期位置失败，并验证修复路径。

仅修改讲解且保留原有示例时，可检查代码、命令、输出及链接的一致性，结合原有运行证据完成核对；不要求为低影响文档修改新增测试或无目的地重跑全部工程。

提交说明应如实交代本次验证了什么、哪些沿用已有结果、哪些尚未验证。不能将未运行、未通过或被跳过的检查描述为通过。

## 10. 必须遵守与灵活安排

| 必须满足的质量要求 | 可按课程需要调整的形式 |
| --- | --- |
| 单课目标清晰，范围能够完成 | 小节数量、标题名称和篇幅 |
| 核心理论足以支撑当前理解与推演 | 使用图、表、关系分析还是执行推演 |
| 实操可跟随，关键动作解释原理 | 完整文件与局部改动的展示比例 |
| 核心小节有小总结，课末有整课总结 | 练习数量、是否设置失败实验 |
| 概念、代码与运行证据一致 | 本课是否进入源码以及进入多深 |
| 边界明确，导航和学习衔接有效 | 辅助段落是否采用三段式组织 |

不设置统一字数、截图数量、测试数量或固定的新术语数量。不能为了格式完整把内容拉长，也不能为了简短省掉核心因果解释。

## 11. 写作、评审与维护流程

开始编写或修改前，阅读本规范、所在阶段和模块大纲、相关前课及模块补充要求，明确当前任务范围、读者已掌握的知识、本课核心机制和验证方式。

写完后按以下问题审阅实际内容：

1. 学生能否说出本课为什么要学、学完能做什么？
2. 理论能否支撑接下来的代码阅读与结果预测？
3. 核心代码旁是否解释了处理过程，而不是仅翻译语法或描述输出？
4. 文件、步骤和运行入口能否连续跟随，错误实验是否回到明确状态？
5. 小总结是否收拢机制，整课总结是否建立了整体理解？
6. 技术结论是否带有必要条件，源码解释是否对应实际版本与分支？
7. 本次验证是否足够支撑交付结论，学习导航是否有效？

这些是质量检查问题，不要求课程正文复制成固定信息卡。若只是添加了“理论”“实操”“总结”标题，而读者仍无法解释因果关系，应继续修改内容。

新课和续写内容从本规范生效后执行；已有课程在本次明确涉及的范围内逐步调整，不因发现规范就擅自重写整个仓库。用户在当前任务中明确的要求优先于本文件；通用教学要求发生变化时，再同步维护本文件，避免模块之间形成不一致副本。
